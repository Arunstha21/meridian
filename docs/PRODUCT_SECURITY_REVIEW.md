# Meridian product and security review

Reviewed: 2026-09-08. Scope: the current working tree, including existing uncommitted product/UI changes. Application code was not changed by this review.

**Recommendation: fix the access-control and money-integrity findings before exposing this installation to untrusted users or relying on its totals.** The architecture has useful foundations, but passing the existing tests does not establish release readiness.

This is a repository-wide, risk-based review: inventory of 197 application source files, with detailed tracing of authentication, authorization, actions/routes, financial services, SQL schema/migrations, exports/imports, MeroShare, AI, background jobs, deployment, tests, and principal product flows. UI findings are from source inspection, not a completed interactive browser/accessibility audit. Generated dependencies were assessed through the lockfile, npm audit, and relevant installed Next.js documentation rather than line-by-line source review.

## Security and privacy findings

### S01 — P0 / High: family export bypasses private-account access

**Reproduced.** `buildFamilyExport` filters accounts, entries, tag links, and shares by `familyId` only. `/api/export` requires a session but no account-permission or email-verification check. A household member denied access to another member's private account can download that account and its ledger.

Evidence: [export service](../src/server/domain/exports.ts#L23), [export route](../src/app/api/export/route.ts#L10), [account policy](../src/server/authorization/access.ts#L111). The probe first confirmed `getAccountAccess(...).granted === false`, then found the account in that actor's export.

**Fix:** export only accounts returned by the centralized access policy and restrict all dependent records to those IDs. Define a separate explicit owner-consent policy if whole-household backups are required; making this admin-only would still contradict the current private-account policy. Check verification at the endpoint.

**Acceptance:** exercise owner, unrelated household member, every share level, revoked share, unverified actor, and cross-family actor against the HTTP endpoint and export service. No hidden account names, entries, notes, or share records may appear.

### S02 — P0 / Critical: invitation flow can grant platform super-admin without inbox control

**Reproduced with synthetic users.** Any household admin can create an invitation for an unregistered address listed in `ADMIN_EMAILS`. The action returns the invitation URL to its creator. Accepting that link with a chosen password sets both `platformRole: "super_admin"` and `emailVerifiedAt`, without proving control of the destination inbox. Enabling email verification does not prevent this invitation path. With verification disabled, direct signup with an allowlisted email is another path.

Prerequisites: an unregistered allowlisted address known to the attacker, and access to household-admin signup/invitation functionality. This grants platform operations privileges; it does not by itself remove every financial-data predicate.

Evidence: [returned invitation URL](<../src/app/(app)/settings/actions.ts#L150>), [invitation registration](../src/server/domain/invitations.ts#L96), [signup promotion](../src/server/domain/users.ts#L71), [verification defaults](../src/lib/env.ts#L22).

**Fix:** remove automatic platform elevation from public registration/invitation flows. Bootstrap/promote platform admins through a trusted operator workflow. A shareable invitation token must not double as proof of email ownership. Decide separately whether public signup should be enabled for a self-hosted household.

**Acceptance:** an ordinary household admin cannot create a platform admin using any invitation or signup route, including when the requested email appears in the operator allowlist.

### S03 — P1 / High: deleting a member exposes their private accounts

**Reproduced.** Removing a member deletes their user row. `accounts.owner_id` uses `ON DELETE SET NULL`; the access policy treats null ownership as a joint account with full control for every household member. A private account therefore becomes shared automatically.

Evidence: [member deletion](../src/server/domain/users.ts#L284), [foreign key](../db/migrations/0001_init.up.sql#L87), [null-owner policy](../src/server/authorization/access.ts#L47).

**Fix:** separate joint-account status from missing/deactivated ownership. Preserve a deactivated owner or require an explicit, authorized disposition of private accounts before removal.

**Acceptance:** removing a user never silently expands the visibility or edit permissions of their accounts.

### S04 — P1 / High: recurring-series reassignment omits source-account authorization

**Reproduced.** `updateSeries` loads a series by family and ID, then checks access only to the merged destination account. A member who knows another private series ID can submit their own account as `accountId` and move the series, even without access to its original account. A read-only share can provide a realistic route to learning series IDs.

Evidence: [updateSeries](../src/server/domain/recurring.ts#L175). The probe moved a private series to a member-owned account with no source-account grant.

**Fix:** require management access to the existing series account and the destination account, inside the mutation transaction. Reject or explicitly convert cross-currency moves; the current update also leaves the stored series currency unchanged.

**Acceptance:** deny reassignment by no-access, read-only, and annotate-only actors; verify source/destination currency and concurrent permission revocation.

### S05 — P1 / High: service worker persists authenticated financial pages

**Reproduced in a VM harness; browser logout scenario inferred from the code.** The worker caches every successful navigation, including account/dashboard/transaction HTML, in a fixed origin-wide cache. It serves those responses offline. Both logout implementations revoke sessions/cookies but do not clear this cache. A shared browser profile can retain an earlier user's financial pages after sign-out. `/quick-add`, which is precached, is also authenticated content.

Evidence: [service worker](../public/sw.js#L30), [registration](../src/components/layout/sw-registrar.tsx#L5), [logout](../src/server/actions/session-actions.ts#L10).

**Fix:** cache only explicitly public static assets and a generic offline page. Remove the existing `meridian-shell-v1` cache during rollout. Avoid caching HTML/RSC/auth routes; changing future caching behavior alone leaves old copies behind.

**Acceptance:** browser test: user A visits financial pages, logs out, network goes offline, user B/back navigation cannot recover A's data. Test an upgrade from the old service worker too. Cache API writes are application-controlled; review [MDN Cache documentation](https://developer.mozilla.org/en-US/docs/Web/API/Cache) when implementing the policy.

### S06 — P1 / High: email-verification policy is not enforced at many mutation boundaries

**Source-confirmed.** Layouts redirect unverified users, but `assertActor()` checks only authentication. Transaction/account actions, organization/member actions, imports, and MeroShare actions use it. A direct Server Action request can reach these operations without passing the layout gate when `REQUIRE_EMAIL_VERIFICATION=true`. Export has the same omission. Budget/recurring actions and chat already apply verification checks.

Evidence: [assertActor](../src/server/auth/context.ts#L69), [transaction action](<../src/app/(app)/actions.ts#L49>), [settings actions](<../src/app/(app)/settings/actions.ts#L118>).

**Fix:** introduce a verified mutation guard and use it consistently for product actions/routes, with explicit exceptions for verification and account recovery. Follow the installed Next.js data-security guide: actions are independently callable endpoints.

**Acceptance:** HTTP-level direct-action tests reject every protected operation for a valid unverified session.

### S07 — P1 / High operational risk: test setup can destroy a non-test database

**Source-confirmed; destructive paths were not exercised on existing databases.** Global setup falls back from `TEST_DATABASE_URL` to `DATABASE_URL`, then drops that database with force. If both variables exist and differ, setup recreates the test database but leaves `DATABASE_URL` unchanged; migrations and integration-test `TRUNCATE ... CASCADE` then target the other database. CI currently configures differing URLs, and `.env.test` points `DATABASE_URL` at `meridian`.

Evidence: [global setup](../tests/setup/global.ts#L4), [truncate helper](../tests/helpers.ts#L47), [test environment](../tests/setup/env.ts#L5), [CI](../.github/workflows/ci.yml#L26).

**Fix:** require a dedicated test URL, unconditionally route every test client/migration to it before imports, reject equality with the application DB, validate/quote identifiers, and use credentials incapable of accessing application databases. Unit tests should not require destructive database setup.

**Acceptance:** configuration-matrix tests cover absent URLs, differing URLs, malformed names, and a sentinel application DB whose tables/data remain untouched.

### S08 — P1 / Medium: authentication throttles trust spoofable forwarding metadata

**Deployment-dependent.** `requestMeta()` trusts the first `X-Forwarded-For` value. Login/reset counters are keyed by IP+email; changing the claimed IP changes the bucket. The provided Compose web port is directly reachable and no trusted-proxy normalization is configured in the repository. Login inputs also have no practical maximum length at the action schema.

Evidence: [request metadata](../src/server/auth/context.ts#L81), [login limiter](../src/server/domain/users.ts#L88), [sign-in schema](<../src/app/(auth)/actions.ts#L16>).

**Fix:** normalize client IP at a trusted ingress, deny direct app access when relying on it, and combine account-level, IP-level, and global throttles. Bound input lengths before expensive work. Avoid permanent account lockout as the sole defense.

### S09 — P1 / dependency risk: upgrade vulnerable direct packages

Audit reports Drizzle ORM 0.44.7 and Nodemailer 6.10.1. Drizzle's identifier-injection advisory is fixed in 0.45.2. The inspected app SQL uses static schema identifiers or fixed allowlisted column text; an attacker-controlled identifier path was **not established**. Nodemailer has several advisories, but Meridian's mail wrapper only supplies `from`, `to`, `subject`, and `text`; do not label unused `raw`/attachment paths as confirmed application exploits.

**Fix:** make deliberate compatibility-tested upgrades, update lockfile and mail typings, and rerun audit plus integration tests. The audit's proposed Nodemailer upgrade was 10.0.1; verify the supported target when implementing rather than blindly using `npm audit fix --force`.

Primary references: [Drizzle maintainer advisory](https://github.com/drizzle-team/drizzle-orm/security/advisories/GHSA-gpj5-g38j-94v9), [Nodemailer maintainer advisory](https://github.com/nodemailer/nodemailer/security/advisories/GHSA-p6gq-j5cr-w38f). Preserve an audit gate and automatic update notifications in CI.

### S10 — P2 / Medium: encrypted provider credentials are included in client props

**Source-confirmed serialization path.** `listMeroShareConnections` selects the entire connection row and retains it in its returned object. The page passes that object to the client `MeroShareManager`. Its narrower TypeScript prop type does not strip `usernameEncrypted`/`passwordEncrypted` at runtime. This exposes ciphertext, not plaintext, to the owning user's browser unnecessarily.

Evidence: [connection query/result](../src/server/domain/meroshare.ts#L552), [client boundary](<../src/app/(app)/settings/meroshare/page.tsx#L23>).

**Fix/acceptance:** explicitly project an allowlist DTO on the server; inspect RSC payloads to ensure no credential fields are transmitted. Add server-only module boundaries where appropriate.

### S11 — P2 / Medium: chat route needs its own CSRF and resource controls

**Conditional exposure, not a demonstrated cross-site exploit.** `/api/chat` is a Route Handler, so Server Action origin checks do not apply. It accepts `request.json()` without checking content type/origin and buffers the body before validation/rate limiting. SameSite=Lax helps against ordinary cross-site POSTs, but same-site hostile origins require separate consideration. Agent calls can run eight rounds with 120-second provider timeouts, without an overall deadline or concurrent-request quota.

Evidence: [chat route](../src/app/api/chat/route.ts#L27), [agent loop](../src/server/ai/agent.ts#L9), [provider](../src/server/ai/provider.ts#L47). See [MDN CSRF guidance](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/CSRF).

**Fix:** validate exact origin/fetch metadata or a CSRF token, require JSON content type, cap streamed request/provider-response bytes, and limit total duration, tool calls, model output, and concurrent work per user.

### S12 — P2 / Medium: tighten identity lifecycle and sensitive-data retention

`changeEmail` immediately changes the login address and leaves existing sessions/reset tokens valid. Reset tokens identify the user rather than the email version; old recovery authority can survive an email change. `performPasswordReset` consumes the token, changes the password, verifies email, and revokes sessions without one enclosing transaction in its action path. Invitation acceptance also consists of multiple non-atomic writes. These are source-level lifecycle risks; race/failure injection was not performed.

Evidence: [email/reset services](../src/server/domain/users.ts#L149), [auth tokens](../src/server/security/auth-tokens.ts#L15), [invitation acceptance](../src/server/domain/invitations.ts#L130).

**Fix:** pending-email confirmation, token invalidation/versioning, atomic recovery and invitation consumption, and recent authentication for sensitive operations. Add explicit retention for auth tokens/chat/proposals. Email jobs store reset/verification URLs in plaintext payloads until cleanup; shorten or remove sensitive payload retention after delivery. Add key-rotation and recovery procedures for MeroShare encryption.

## Suggested delivery order

1. **Contain access risks:** S02 platform-admin bootstrap, S01 export policy, S05 cache eviction, S03 ownership transition, S04 recurring authorization, and S06 verified mutation guard. Correct S07 before relying on any new CI tests.
2. **Restore trust in money:** split/transfer invariants, liability signs, currency conversion/form scaling, long-history balances, and atomic recalculation. Add regression fixtures for each concrete failure.
3. **Make the release operable:** dependency upgrades, lint/format gates, production mail/DB defaults, restorable backup, and accurate incomplete-data warnings.
4. **Improve daily use:** privacy consistency, actionable errors, budget editing, transaction correction, accessibility/localization, and explainable metrics. Add larger features only after these foundations are dependable.

## What is already working well

- Most account and report queries implement household plus owner/share restrictions; platform role alone does not grant those permissions.
- Session/reset tokens have strong random values with hashes stored in auth tables; password checks use scrypt and constant-time comparison.
- Many foreground ledger actions wrap mutations and recalculation in database transactions.
- AI writes require an expiring, user-owned proposal and explicit confirmation; claim plus ledger write share a transaction.
- MeroShare uses AES-GCM encryption, a fixed upstream host, rejected redirects, timeouts, and streamed response-byte caps.
- Sure import bounds archive/extracted sizes, accepts a specific archive entry, and imports within a transaction.
- CSP nonces and other response headers are implemented; the production build and existing test suite pass.

Re-test the fixed version and deployed configuration before making a security-readiness claim. Keep dependency checks ongoing because advisories change.
